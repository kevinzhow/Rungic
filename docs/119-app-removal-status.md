# App 识别未完成的卸载

对应 task #45，独立于卸载工具 task #35。App 在请求重新发布安装状态、首次安装检查和 Linux 启动之前，直接通过现有 root 通道读取 `/data/adb/rungic-uninstalling`，不依赖已经删除的控制器或 runtime。

空标记、非空标记或该位置的符号链接都显示“Rungic 卸载未完成”，提示在连接的电脑上重新运行卸载，不显示可以在 App 内完成卸载的重试动作。只有明确读到无标记才继续普通入口。新的查询先确认 root 身份，再成功读取 `/data/adb` 的目录项并精确匹配标记名称，不把标记内容不可读或悬空链接误判为不存在。权限失败、10 秒超时或未知输出显示“无法确认”，允许检查超级用户权限后重试，且不进入安装或启动。

查询只读，不创建标记、不删除文件、不完成卸载。原 root 控制器通道的非零退出继续抛错；未知响应也抛错。卸载的状态及最终清理仍由卸载工具管理。

`RemovalStateTest` 验证明确存在、明确不存在和未知响应；`tools/ci/test_app_removal.py` 在 Bash 与 BusyBox ash 的真实临时文件系统执行同一固定查询，验证控制器不存在时的空／非空标记、无标记、悬空链接以及非 root、身份命令失败和父目录不可读。Android su 与 UI 呈现不是这些实验的证明范围。

尚待真机：打开卸载中断现场的 App，观察中英文提示与超级用户拒绝／授权；卸载完成后重新打开，核对普通安装入口恢复。本轮开发不得据本地编译和替身实验声明真机体验通过。APK 发布及部署需要独立候选评审与授权。
